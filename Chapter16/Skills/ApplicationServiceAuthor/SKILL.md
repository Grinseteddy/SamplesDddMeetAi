# Application Service Author

Builds the application layer of one bounded context with **EXACT Coding** —
Predictive TDD v1 by Ferdi Ade and Marco Emrich
(github.com/marcoemrich/EXACT-Coding-Exercises, MIT). EXACT Coding supplies
the method; this skill supplies **what the use-case and policy test lists
must cover** and **what shape** the application layer must have.

The application layer **orchestrates**; it decides nothing the business would
call a rule. Every rule lives in an aggregate (step 6) or is a policy with a
name from the invariants sheet.

Works inside **blueprint-service-implementation** (step 8), which hands over
the inputs and owns the step checkpoint. It also works on its own; then ask
for the inputs one at a time.

## Inputs

| Input | Required | What is used from it |
|---|---|---|
| The **aggregates** from step 6 | yes | command methods, factories, typed IDs, rejections, `pullEvents` |
| The **repository ports** from step 7 (and the unit of work, if one exists) | yes | `findById`, `save`, `ConcurrencyConflict`, transaction scope |
| The **design brief** (step 2) | yes | commands → aggregate, policies (*whenever event X, then command Y*), external systems |
| The **invariants sheet** (step 3) | yes | rules marked as **policies** (cross-aggregate or cross-context), their staleness window and compensating action; authorization rules |
| **ADRs** (step 5) | yes | idempotency strategy, retry on conflict yes/no, time source, ID generation, authorization model |
| **AsyncAPI** subscribed channels | if policies react to other contexts | message identity (message ID field) for idempotency |
| An **approved inactive test list** | optional | use it as is |

Missing a required input: say which, and stop for it. A skipped ADR this
layer needs (idempotency, retry, ID generation): ask it now; if skipped
again, use the default below and report it as an open risk.

**Defaults when an ADR stays open:** no automatic retry on
`ConcurrencyConflict` (it propagates; step 9 maps it to 409); idempotency of
policy handlers by a processed-message record keyed by message ID, written in
the same transaction as the aggregate; IDs generated by an injected
generator; time from an injected clock.

## 1. Check the slice

Show, before any test: each command → its use case → aggregate method; each
policy → triggering event (own or from another context) → command it issues
→ staleness window and compensation from the invariants sheet; the
authorization rules and the actors they name. Flag and ask about:
- a command no aggregate method serves, or a method no command calls;
- a policy with no triggering event, or one whose command does not exist;
- a policy that reads another aggregate's state **synchronously** to decide —
  name the read model or query port it needs and the staleness it accepts;
- a rule placed in the brief as "the service checks …" — it belongs in an
  aggregate or is a policy; ask which.

## 2. Test doubles first: fakes that keep the contract

Use cases are tested with **in-memory fakes** of the repository ports, a
fixed clock and a predictable ID generator — never with mocks of the
aggregate, and never with a database (that was step 7).

A fake is only trustworthy if it behaves like the real adapter. So the
**first unit** is the fake repository, and its test list is the **repository
contract** from step 7, run against the fake:
1. `findById` of an unknown ID returns absent;
2. a saved aggregate is found again equal, with no pending events;
3. saving increments the stored version by 1;
4. the second of two concurrent saves fails with `ConcurrencyConflict`;
5. `save` records the pending events (the fake's stand-in for the outbox).

Give the fake one test hook for concurrency — e.g. `interleave(fn)`, run once
inside the next `save` before its version check — so a use-case test can
simulate another writer without hand-built wrapper objects.

Where the stack allows, write this contract **once** as a shared suite and
run it against both the fake and the real adapter, so they cannot drift.
Same for the unit of work and the processed-message store if they exist.

## 3. Test lists — EXACT `test-list`, with application coverage

One unit per **aggregate's use cases** and one per **policy**. Each test
file holds every behavior as an **inactive test**, ordered simple →
complex, expected values in the description, the trace after `--`
(`-- B1-S03 US-07 cmd BorrowCopy`, `-- B1-S05 US-08 policy P-02`,
`-- B1-S03 US-07 ADR-011`). Treat **commands,
policies, outcomes (ok / not found / rejected / conflict / duplicate) and
authorization rules** as EXACT's independent dimensions.

**Per command use case**
1. happy path: the aggregate is loaded (or created), the command method
   called, the aggregate saved, and the result returned (new ID, or nothing,
   as the OpenAPI response needs);
2. the events the aggregate raised were saved with it (visible in the fake);
3. **not found**: unknown aggregate ID → `<Aggregate>NotFound` (an
   application error, mapped to 404 in step 9), nothing saved;
4. **rejected**: each domain rejection the command can raise passes through
   **unchanged** (same type, same rule ID), nothing saved — one test per
   rejection, not per rule inside it (the rules were tested in step 6);
5. **conflict**: `ConcurrencyConflict` on save propagates — or, if the ADR
   chose retries, the use case reloads and retries up to N times and then
   propagates; one test each;
6. **creation**: the new ID comes from the ID generator; creating with an ID
   that exists → the rejection or error the ADR names;
7. **authorization**, per rule the invariants sheet names for this command:
   an actor without the right is refused with `NotAuthorized` before the
   aggregate is loaded;
8. **idempotent commands**, only if the spec declares an idempotency key:
   the same key twice → one effect, the second call returns the first
   result.

**Per policy handler**
1. the triggering event → the right command on the right aggregate, with the
   values the event carries;
2. **idempotency**: the same message (same message ID) twice → one effect;
   the processed-message record is written in the same transaction as the
   aggregate;
3. the event refers to an aggregate that does not exist → the ADR's choice
   (ignore and log, dead-letter, or create) — one test;
4. the command is rejected by the domain → the compensating action from the
   invariants sheet, or a logged, named outcome if none is defined — never a
   silent swallow;
5. events from another context are translated by the anticorruption mapping
   **before** the handler (step 9 owns the mapping); the handler receives
   own-language input only.

Apply EXACT's Test-List checkpoint per unit. The approved list is the scope.

## 4. Cycles — EXACT `exact-coding`

Run EXACT Coding's Predictive TDD cycles as written — **one
behavior per activation**, even when the next two items need the same new
type: scaffold the type, observe the first item, then activate the second.
Activating two at once lets one import error hide both results.

Expect the **guard tests** — rejection passes through unchanged, conflict
propagates — to be green on activation: a use case that catches nothing
already satisfies them. EXACT treats that as legitimate evidence; keep them,
they fail the day someone adds a catch block that loses the rule ID.

In EXACT's domain-responsibility review, the strongest signal at this layer
is a **business decision inside a use case** (an `if` on aggregate state, a
calculation, a threshold). Its boundary trial is always the same: move the
decision into the aggregate (back to step 6, test-first there) or name it as
a policy. The use case keeps only orchestration.

**Fast loop.** This skill runs EXACT's cycle with the two adaptations
`blueprint-service-implementation` makes (the same in every step skill;
standalone, they apply too unless the user asks for EXACT's original):
- **Predictions cover behavior.** Before every check, say which tests fail
  or pass and why — the failing assertion or error you expect, and for a
  Red that it fails for the behavioral reason. Gates (type check, lint,
  format, architecture rules) are predicted only as pass or fail. Never
  predict test counts, lint totals, line numbers or durations; lint rules
  that report every function (cognitive complexity with threshold 0 as a
  "measurement") are off in the loop and reported once at the finish.
- **Fast suite per cycle, slow suite at the finish.** Each cycle runs the
  unit's own test file, the fast suite (tests without containers or
  network) and the type check. The slow suite (real database, broker, end
  to end) and every gate of the stack profile run at the finish and before
  every commit — twice in a row only for tests that touch concurrency or
  timing. Containers start once per test run and are reused.
- **Trials** (break the code, predict the failure, restore) only for a test
  that is green on activation and once per new gate.
- **Traces** start with the slice and the user story it serves:
  `-- B1-S03 US-07 …`; several user stories as `US-07,US-09`.
- **Walking skeleton (increment 0):** list and build only what the skeleton
  slice needs; everything else goes on the blueprint's planned list.

## 5. What the finished application layer shows

- **One use case per command**, named after it (`BorrowCopy`), with one
  public method (`execute` / `handle`) taking a **command object** of
  domain types (typed IDs, value objects) — not HTTP DTOs, not message
  classes; step 9 maps those.
- The body is **load → call → save → return**, nothing else. One aggregate
  per use case and per transaction.
- **Errors**: `<Aggregate>NotFound` and `NotAuthorized` are application
  errors; domain rejections and `ConcurrencyConflict` pass through
  unchanged. No catch-and-rethrow that loses the rule ID.
- **Policies** as handlers named after the policy (`NotifyMemberWhenCopyBorrowed`),
  each issuing commands through the use cases (or the aggregate directly,
  in the same shape), idempotent by message ID, compensating as the
  invariants sheet says.
- **Ports in, adapters out**: use cases depend on repository ports, the
  clock, the ID generator and query ports — never on a concrete adapter,
  ORM, HTTP client or broker.
- **No framework in the application classes** unless an ADR allows it:
  plain classes, wired by the framework in the infrastructure layer.
- **Trace comments** on each use case and handler:
  `// cmd: BorrowCopy · agg: Copy` / `// policy: P-02 · on: CopyBorrowed`.

## 5a. Finish

1. EXACT's completion: all tests active, all profile gates green,
   behavioral mismatches explained; the fast and slow suites green; the shared repository contract green for **both**
   the fake and the real adapter.
2. Checks, shown with output:
    - no business decision in the application folder that the report cannot
      justify (list every `if` in a use case and say what it decides);
    - no infrastructure imports in the application layer:
      TypeScript `grep -rnE "from ['\"](pg|typeorm|@prisma|drizzle-orm|kafkajs|amqplib|axios|express|@nestjs)" src/*/application`;
      Java/Kotlin `grep -rnE "jakarta\.persistence|org\.springframework\.(data|kafka|amqp|web)|java\.net\.http" src/main/*/**/application`.
3. **Wiring**: register use cases, handlers, repositories, clock and ID
   generator in the framework's module or configuration (infrastructure
   layer), and add **one** wiring test per use case group that runs the happy
   path through the real adapter (step 7's database setup) — the only test
   here that touches a database.
4. Report: EXACT source and autonomy level; tests active/total per unit;
   behavioral prediction mismatches; commands → use cases, policies → handlers;
   idempotency, retry and authorization decisions with their ADRs; business
   decisions moved back to the domain; open risks; files created.
5. Return to the caller's unit checkpoint, or ask the user to approve.

## 6. Stack idioms

### TypeScript + NestJS (default)

- Folder `src/<context>/application/` — one file per use case and per policy
  handler, plus `ports/` for clock, ID generator and query ports.
- Use cases as plain classes with constructor-injected ports:
  `class BorrowCopy { constructor(private copies: CopyRepository) {} async execute(cmd: BorrowCopyCommand): Promise<void> }`.
- NestJS wiring in `src/<context>/infrastructure/<context>.module.ts` with
  `useFactory` providers and injection tokens for the port interfaces
  (`{ provide: COPY_REPOSITORY, useClass: PgCopyRepository }`), so the
  application classes stay free of `@Injectable` unless an ADR allows it.
- Fakes in `test/fakes/` (or next to the specs): `InMemoryCopyRepository`
  storing **state snapshots** and versions, rebuilding through
  `reconstitute` on load — never handing out the same object it stored.
- Shared contract suite as a function, e.g.
  `copyRepositoryContract(name, make)` in `test/contracts/`, where `make`
  returns the repository and a way to read the saved events (the fake's list,
  or the outbox table). Call it from the fake's spec and from a database
  spec. Test files that share one test database must not run in parallel:
  give each its own database name, or run them with `--no-file-parallelism`.
- Vitest: a file of only `it.todo` reports as *skipped*.

### Java + Spring Boot (second option)

- Package `<base>.<context>.application`; use cases as plain classes; Spring
  wiring with `@Configuration` / `@Bean` in infrastructure. `@Transactional`
  goes on the infrastructure adapter or a configured transaction template,
  not on domain classes; on the use case only if an ADR allows Spring there.
- Fakes implementing the port interfaces; the shared contract as an
  abstract JUnit 5 test class extended by the fake's test and the
  Testcontainers adapter test.

### Kotlin + Spring Boot (third option)

- As Java; use cases as classes with `operator fun invoke(cmd)` if the team
  prefers; `Result` or sealed outcomes only if the ADR chose them over
  exceptions. EXACT has no Kotlin profile — use the Java profile adapted to
  Gradle, and say so.

## 7. Never

- Put a business rule, calculation or state check into a use case.
- Load or save two aggregates in one transaction.
- Swallow a domain rejection or lose its rule ID.
- Test use cases against mocks of the aggregate, or against a fake that has
  not passed the repository contract.
- Import an adapter, ORM, broker client or HTTP type into the application
  layer.
- Report a test result that was not run.

## 8. Fallback (only if EXACT Coding cannot be located)

The same inactive test lists. Per behavior: predict, Red for the predicted
reason, least code to Green with the unit's tests and the fast suite (slow
suite and gates at the finish), refactor under the Four
Rules with §5 kept; show and ask before the next behavior.
