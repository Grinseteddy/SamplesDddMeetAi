# Architecture Communication Canvas [Bounded Context]

## Value propositions

> They can be taken out of the Impact Map, if the domain knowledge graph contains one. 
> Otherwise, they need to be derived from existing Domain Stories or EventStorming boards.

## Core functions

> The core functions can be taken out of the Domain Stories valid for the current Bounded Context.

## Key stakeholders

 > The key stakeholders appear in the Impact Map. 
 > If no Impact Map is available, the stakeholders need to be derived from the ADRs and the Domain Stories.
 
## Quality requirements

> Quality requirements appear in the implementation ledger, in the ADRs, and quality scenarios.\
  
## Core decisions

> The core decisions are reflected in the architecture graph. 
> However, they might be overridden during implementation; therefore, a reference to the implementation ledger is necessary.

## Technologies used

> The technologies are listed in the implementation ledger and ADRs.
  

## Business context

> The business context can be derived from the Context Map showing the data flow.
  It can be shown as a C1 (system context) diagram of the C4 model.

## Components and modules

> The components and modules can be derived directly from the code or from the implementation ledger. 
> They can be shown as a C2 (container) diagram of the C4 model [@brown2026c4].

## Core risks and missing information

> The risks can be derived from the implementation ledgers and superseded ADRs out of the corresponding Bounded Context.
